# Payment request review and handoff

This is an incomplete stage toward the owner's voice payment workflow, not a completed transfer capability. Google's [Android UPI integration](https://developers.google.com/pay/india/api/android/in-app-payments) documents merchant URI fields and package-pinned Google Pay handoff. It requires PSP/aggregator verification before treating a payment as paid. AIVORA has no backend, bank credentials or payment-status authority. PhonePe generic-UPI acceptance and physical Google Pay acceptance remain unverified; neither is represented as a completed payment integration.

An explicit owner command, `review payment <upi://pay?...> using Google Pay` (or PhonePe), parses only an exact INR merchant request containing pa, pn, mc, tr, am and cu, with optional tn/url. No merchant code, reference, payee identity or signature is invented. Unknown/repeated fields, malformed/oversized/unsafe text, unsupported currencies, fractional paise, zero/negative amounts and insecure transaction URLs refuse. Decimal conversion uses exact integer paise. Public names/addresses are user-provided, not bank-resolved identities. Parser limits are structural bounds, not claims about bank transaction limits.

The immutable typed request is CRITICAL risk, network-required and strict-codec. Existing policy requires Android device authentication followed by rotated exact-plan confirmation. Review includes all transmitted fields. Complete review prompts now support up to1200 characters without truncation; larger prompts retain full on-screen review. The existing deadline is not extended, and stale/interrupted speech cannot proceed to reply capture. Physical identifier pronunciation, owner hearing/approval and complete voice payment acceptance remain unfinished. A payment is reviewed alone, never mixed with other actions, taught as a reusable merchant reference or scheduled. No worker or routine can replay a saved checkout request.

Only a newly reconstructed allowlisted URI is sent to the explicitly chosen app package. No browser/other-app fallback is allowed. Return is REQUIRES_USER_INTERACTION; activity launch, callback strings and notifications are not authoritative settlement evidence. There is no Pay click, PIN capture, payment-app authentication bypass, successful-payment state or automatic retry. App rejection, merchant registration/expiry and bank-resolved recipient checks remain external acceptance work. Core still has no INTERNET permission.

Verification must cover exact amount/fields, URI injection/duplicates, codec and policy, lock/unverified/replay refusal, unavailable apps and package-pinned intent payload without launching a real payment. No test may transfer money as an incidental integration check. Actual payment-app/bank acceptance, named personal recipients, voice amounts/payee clarification, QR import, user-approved payment completion and authoritative status remain incomplete.

Payment speech now spells all supplied identifiers/text fields using explicit case/digit/space/punctuation names. Exact amounts use integer Indian rupees plus hundredths of a rupee, with no guessed lexicon phonemes. Printable ASCII is currently required for complete spoken payment review; Unicode or expanded prompts over1200characters fall back to complete UI review. No request value or bank identity is changed by the speech representation. See SPOKEN_PAYMENT_FIELDS_DESIGN.md.
