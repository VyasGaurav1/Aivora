# Expanded owner goal

The owner requests a fully offline voice-controlled phone assistant, with connectivity used only when a requested task requires it, permission setup and device/app analysis on first launch, and voice workflows including unlocking, YouTube, messaging and payment apps such as GPay and PhonePe. This extends the original BUILD_SPEC.md; it does not replace its offline, identity, verification or policy requirements.

The complete goal is not achieved. Required work and acceptance evidence include:

- Offline voice: protected enrollment, wake, owner verification, recognition, reasoning, memory and speech must work on physical phones without connectivity. Existing emulator/model tests are insufficient for microphone/OEM acceptance.
- First launch: explain and request required Android permissions, detect supported capabilities and launchable apps, expose denials and unsupported features, then guide voice/wake enrollment. The setup screen now covers permission review and initial capability/app discovery; richer special-access and voice enrollment guidance remains incomplete.
- Connectivity: determine whether the requested task needs it, use the configured owner policy, observe actual connectivity, enable only through supported platform or explicitly authorized privileged mechanisms, and report verified results. Typed online actions use the configured policy, validated-network observation and an expiring single-use pending task that resumes through action policy when AIVORA is foreground/unlocked. Separate opt-ins now support confirmed Wi-Fi and authenticated single-ready-default-SIM mobile-data controls through the known Android Internet panel. Wi-Fi radio state, mobile-data user setting and actual validated internet are separate observations. Multiple/changed/hidden/locked SIMs and roaming enable requests are refused. Silent APIs, SIM/network/password selection, automatic restoration, real credential/voice and physical/OEM acceptance remain unfinished.
- App control: build typed, scoped semantic adapters and observe outcomes for YouTube/video, messaging and other requested workflows. YouTube title requests currently open search and exact supported links request a video. Existing-video play/pause now prefers authorized YouTube media sessions and has an owner-enabled scoped accessibility fallback with strict state checks; compatible-device positive playback acceptance and result selection remain unfinished. Named WhatsApp/Business drafts now preserve exact app/contact/body through clarification and policy using supported click-to-chat links; automatic send and delivery verification remain unfinished. Discovering/opening an app does not establish control of its features. Draft/sharing handoffs are not confirmed sends.
- Unlock/authentication: provide legitimate Android authentication and assistant invocation flows. Speaker recognition must never be represented as Android lock-screen authentication or used to bypass a PIN, password or biometric requirement.
- Payments: implement a typed payment intent/review/handoff workflow with exact recipient, amount and app checks. It must not store UPI PINs or banking credentials, bypass payment-app authentication or claim a transfer succeeded without authoritative evidence. Typed CRITICAL merchant-link review and explicit-app URI handoff are now implemented, with authentication then exact confirmation and no payment-completion claim. Payload/policy tests do not prove actual app acceptance, transfers, personal-recipient payments or complete spoken payment approval.
- Hands-free acceptance: test complete real-device command sequences, interruptions, false speakers, unavailable network/apps, changed targets, lock state, canceled approvals and permission revocation. Identify all remaining owner-required system interactions honestly.

Permanent product identity remains AIVORA / com.chronoit.aivora. Assistant display/wake names remain independent and default to Aivora.

- Calling: optional typed direct cellular calling, public caller-SIM/account binding, runtime permissions, Android authentication and exact confirmation now precede system Telecom. Emulator-only call state is verified; physical connection, owner voice, incoming/end-call management, multi-SIM and other remaining calling workflows are incomplete.
