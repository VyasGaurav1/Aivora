# Supported Wi-Fi Internet-panel controls

The owner's task-driven connectivity goal now has a user-visible Android Internet-panel adapter. This is not a privileged radio API. Mobile data has its own separately opted-in, authenticated single-SIM adapter (see MOBILE_DATA_DESIGN.md). Wi-Fi network/password selection, general Settings automation and automatic restoration remain unfinished.

## Authorization and task flow

`Action.SetWifi` is typed, offline, strictly serialized and medium risk. It uses normal source/lock/audit policy and fresh exact-action confirmation. A separate `wifi_controls` preference defaults to false. The owner must enable this opt-in and bind AIVORA's app-controls AccessibilityService through Android. Existing YouTube access alone does not opt into Wi-Fi changes.

For an approved online task, ConnectivityOrchestrator exposes its original trusted source only for the matching current approved token. If Wi-Fi is known off and the adapter is opted in and bound, the ViewModel requests a separate confirmed Wi-Fi action. It retains the original task registry, including scheduled-action guards. Completion queues a network recheck after the Wi-Fi helper job finishes, covering the case where network/lifecycle callbacks occurred while that helper was still active. Original work resumes only with validated internet and resumed, unlocked AIVORA. Cancellation/replacement invalidates pending work. Unknown state, missing opt-in/service or an already-enabled but disconnected radio retains the existing system-controls fallback.

Spoken permission to connect is separately bound to the token, plan ID, source and deadline present before reply capture; stale replies cannot approve a replacement request. The dialog can read a complete short task and capture a verified reply, while showing the full description for on-screen review. See NETWORK_VOICE_APPROVAL.md.

## Narrow Internet-panel interaction

The adapter pins `Settings.Panel.ACTION_INTERNET_CONNECTIVITY` to the installed system `com.android.settings` app, which opens the System UI Internet dialog on the tested API35 emulator. The selector requires the exact `com.android.systemui:id/internet_dialog_title` Internet heading, `wifi_toggle_title` Wi-Fi label, and unique checkable clickable `wifi_toggle` Switch. Checkbox state must match the independently observed stable WifiManager state. The full Wi-Fi Settings page returned no usable root to this non-accessibility-tool service during testing; that page is not an alternate selector or a reason to relabel the service.

The service allows snapshots only for YouTube or System UI; it still has no gesture capability, interactive-window enumeration or continuous event capture/logging. Internet-panel snapshots store structural properties and booleans for exact known Internet/Wi-Fi/Done labels. Other title values, SSIDs, notification text and content descriptions are not retained. Password nodes are not read, and any password screen, truncated/budget-exceeded tree, wrong package, ambiguous/changed control or unknown structure is rejected. Existing 500-node, depth24 and 500ms snapshot bounds remain.

Before the one switch click, a fresh snapshot/window is compared and the actual switch ID/class/state, radio state and lock state are rechecked. The service also rechecks the opt-in and interruption state. There is no coordinate, arbitrary-label, mobile-data or password-entry fallback. After the click the adapter polls WifiManager for the requested stable radio state. Only that independent observation supports radio success; it never establishes internet access. It waits for the matching panel state, validates and clicks the unique known Done button, then requests return to the existing AIVORA activity. It does not dismiss an unrelated dialog. The normal task layer separately checks validated connectivity.

## Acceptance

Pure tests cover selector ambiguity/structure/password/package/state changes, strict parser/codec, medium-risk confirmation/source/replay and approved-task source binding. Ordinary Android tests check the expanded protected service scope and that opting out refuses the action before a Settings handoff or radio change.

WifiSettingsProbe is an explicit isolated-emulator test, excluded from the ordinary suite rather than counted as skipped. It temporarily binds the service, checks a real Internet-panel Wi-Fi-off interaction, removes mobile connectivity, and checks a confirmed Wi-Fi-on helper. The saved emulator Wi-Fi network has no validated internet: the test verifies the original search remains unexecuted in that state, then restores mobile connectivity through the test harness and observes validation plus the original YouTube search handoff. This does not prove that Wi-Fi provided internet, that AIVORA switched mobile data, that voice recognized approval, or that video played. The probe restores saved radio/preferences/service settings. Earlier probe failures exposed full-page root refusal, a cleanup-masked failure and panel-dismiss/validation assumptions; only the corrected successful probe is acceptance evidence. Physical/OEM/API/layout/language coverage, interruption/revocation during the switch, cancellation before/after effects and battery acceptance remain required. No complete hands-free or full-application claim follows from a narrow adapter test.


Android11 extension design: API30 uses the system Settings Internet Connectivity panel instead of the newer System UI dialog. Only API30 adds Settings to service event packages, with no other service flags/gestures/window enumeration changes. Bounded snapshots retain only known-label booleans and structural metadata, never SSIDs/other Settings text. A legacy selector requires the observed flattened root FrameLayout, unique direct panel_title/panel_parent_layout children and exact Internet Connectivity title, one exact Wi-Fi label as a direct child of a known row_view under its slice_view, one direct Switch sibling in that row, expected state and a unique direct known Done button. The actual service tree flattens the UI dump's panel_container and widget_frame; those unexposed wrappers are not inferred. Fresh window/path/structure/live radio/lock/opt-in checks still gate every click. Other Settings pages and multiple/hidden controls refuse. Newer Android service scope remains unchanged. Native off/on and panel dismissal must pass a separate API30 probe before claiming acceptance; older mobile-data panel controls are not implied.
