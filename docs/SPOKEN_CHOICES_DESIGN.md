# Spoken contact and file choices

Ambiguous contacts and files can be resolved with explicit replies such as `the second contact`, `choose contact number two`, `the first file`, `select document twenty`, or an option number. Number words and ordinals one through twenty are recognized; digit replies use one-based list numbers. A choice selects a target for planning, not permission to execute the resulting action.

VoiceChoiceGate records the current choice kind, random request token and list count when voice capture is prepared. It consumes that binding once only for a VERIFIED_VOICE reply, and rejects a changed token/kind/count, out-of-range number, unverified source, mixed choice lists or replay. New commands and cancellation clear the binding. The automatic foreground wake path arms it after the verified wake, before command capture. A fresh contact list after a file selection requires another captured reply.

Verified opted-in requests can automatically read the choices and listen once for a reply. The dialogs also expose `Read choices and reply`. Readouts use three entries per page, retain global numbering and include contact label/number or file MIME type/size. `next choices`, `previous choices`, and `read choices` navigate or repeat without selecting a target. Paging itself is token-bound for voice input. Full page text must fit the 1200-character speech budget; oversized descriptions request a narrower command or on-screen review, without silently truncating an option. Readouts remain local and are not learned or persisted as new memories.

The existing two-minute pending-choice deadline still applies and is not extended by paging. Readback checks the current dialogue token and deadline before starting, and resolution rechecks the deadline. Expired/changed requests require repeating the complete command. Invalid current-list replies preserve the choices so the owner can capture a corrected answer.

Resolution uses the existing DialogueCoordinator and fresh policy/registry path. Contact app/number/body and file identity are retained; file access and current contacts are rechecked by existing execution guards. Medium-risk actions still need exact-plan confirmation; sharing still requires Android authentication followed by confirmation. Share/message handoffs do not establish sends or delivery. A choice within a scheduled request retains the original schedule, conditions and recurrence; it must not become an immediate action merely because the owner answered a clarification.

Pure tests cover grammar, pages/global numbers, captured-list replacement/source/replay, message payload preservation, chained file/contact choices, access loss/expiry and authentication/confirmation policy. API35 instrumentation uses real temporary contacts and injected VerifiedVoiceCommand results at the production callback boundary to verify ViewModel paging, list replacement refusal, selected payload and future scheduling. Injection is not evidence of microphone recognition or speaker verification. Physical spoken clarification, short replies, echo, large/long lists, translated names and OEM acceptance remain required.
