# Mobile-data controls

The requested offline core may use mobile connectivity for approved tasks, but enabling data may incur carrier charges. The implementation uses a typed high-risk action, real Android authentication followed by exact-plan confirmation, and a separate default-off opt-in. It never uses a privileged radio setter or shell command in production.

The initial target is one ready, active, non-opportunistic subscription matching the default data subscription. Permission READ_PHONE_STATE is requested for SIM identification. The Android 11+ baseline checks the [complete active subscription list](https://developer.android.com/reference/android/telephony/SubscriptionManager#getCompleteActiveSubscriptionInfoList()), including hidden subscriptions. A snapshot binds subscription ID, SIM slot, carrier ID and display label; the live tuple and readiness are checked before and during execution. No phone number, ICCID, IMSI, banking credential or SIM PIN is read/stored. These public metadata are a live subscription binding, not a cryptographic identity of physical SIM hardware. Multiple/changed/unavailable subscriptions and roaming enable requests are refused rather than guessed.

The adapter opens the known system Internet panel and matches only its unique mobile toggle, Internet heading and exact independent SIM label. It revalidates source window/path/control/state and live subscription before one click. Disabling may show the observed English System UI warning; only its exact title, SIM-specific message and Turn off button can complete that already-authorized action. Unknown dialogs, password screens, changed targets, lock, interruption and opt-out fail closed. Only known-label booleans are retained from this panel; no notification/SSID text is collected.

TelephonyManager.isDataEnabled reports the user mobile-data setting, not radio connectivity or internet availability ([Android reference](https://developer.android.com/reference/android/telephony/TelephonyManager#isDataEnabled())). Success therefore describes that setting only. Validated internet is separately required before original online tasks resume. A known Done button closes only the matching panel, then returns to the existing AIVORA activity. There is no automatic restoration, roaming approval, SIM switching or general Settings automation.

Acceptance must include typed codec/validation, device-authentication-before-confirmation, target changes, permission/opt-out and scoped-selector failures, plus a separate isolated-emulator adapter probe of actual off/warning/on and observed per-subscription state. Adapter tests do not establish real Android credential completion or physical voice approval. Physical/OEM/locale/dual-SIM/eSIM/roaming, revoke/interrupt and cost acceptance remain required; the full goal is not complete.


API30 extension design: use only the observed flattened legacy Internet Connectivity panel. Require one exact Mobile data heading, its known slice/row hierarchy, one direct same-row SIM summary exactly matching independently supplied live subscription display metadata and one direct switch. All existing single-ready-default-SIM, permission, roaming, lock, fresh window/path and opt-in guards remain mandatory. This emulator disables data directly without a warning; unknown dialogs remain unsupported, and the newer SystemUI exact warning path stays unchanged. Known Done must match the complete same-SIM panel. Verify native off/on and validated cellular original-task resumption separately on API30; injected Android authentication is routing evidence only.
