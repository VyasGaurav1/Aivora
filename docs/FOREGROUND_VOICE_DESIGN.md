# Repeated foreground wake listening

The Voice screen provides an explicit runtime-only "Keep listening while open" control. It requires microphone permission, enrolled owner/wake profiles and hands-free opt-in. It is not saved as an instruction to start recording on app launch or after process death. The normal one-minute listener and separately user-started background service remain available.

ForegroundWakeLoop owns the specific wake capture it started. Every capture is bounded to sixty seconds; when it ends the loop rechecks readiness and can start another. Idle capture uses the lightweight wake templates and a short zero-cleared RAM ring through BackgroundWakeListener. STT runs only after wake matching and speaker verification, followed by the existing second owner check for the actual command.

Readiness requires a resumed, visible, unlocked activity, opted-in controls, no current command work or device-authentication review, no enrollment/other capture/speech, and an available shared microphone lease. Loss of readiness cancels the loop's owned capture. Activity pause explicitly suspends readiness polling until resume. Other captures/replies are not owned by this loop and are not canceled by its pause/stop operations. The actual lease still arbitrates races between components; a transient busy lease waits rather than disabling the mode. Other processing failures stop the mode with local error feedback.

Automatic idle listening does not call the manual capture hook, which could cancel an in-progress owner task. After a verified wake, it checks readiness again and binds any pending action confirmation immediately before command capture. New commands use the same verified grant and ActionRegistry path. Exact-plan approval, expiry, authentication and lock checks remain in force. Automatic listening pauses for real Android authentication, and successful authentication returns to the existing review path.

Normal requests, replies and legitimate external-app handoffs pause or interrupt capture while retaining the runtime opt-in. Returning to an eligible foreground activity can resume wake listening. Explicit Stop/Cancel, removing profiles, beginning enrollment, disabling hands-free controls and ViewModel closure stop the mode. The background wake service continues to pause while AIVORA is visible; this mode does not extend its permissions or bypass Android activity/lock rules.

Verification separates control-loop evidence from voice acceptance. Pure tests cover no overlapping captures, readiness loss, bounded-capture restart, ownership, stopping and immediate restart generation. An isolated API35 instrumentation test uses test-only encrypted profiles, real AudioRecord recording-configuration observation and the shared lease to verify waiting, microphone startup, pause, resume, stop and release. It does not feed a spoken command or prove wake accuracy, owner recognition, command execution, liveness, battery use, permission-dialog UX or physical/OEM acceptance.
